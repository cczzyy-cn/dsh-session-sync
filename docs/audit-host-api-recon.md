## Q3 — Does a newly written log appear without a restart?

**Nothing watches the sessions directory.** `grep 'chokidar|fs.watch|watchFile|FSWatcher'` over `packages` hits only credentials/hmr/fs-local/skill-filesystem/client-hmr/webworker-runtime — never a session package. A log written straight through `sessionPersistence` raises none of them.

**Explicit refresh APIs:** client-side `ctx.sessions.refresh(): Promise<void>` (`api/session-controller/src/client/contract/sessions.ts:105-109`; impl `client/sessions/service.ts:353-355`). ## Q7 — Appending to an ALREADY-EXISTING session log (post-restart)

**Yes — a write handle for an existing id exists:** `SessionPersistence.open(id, 'write', options?): Promise<SessionHandle>` (`session-persistence/src/index.ts:165`; jsonl impl `index.ts:342-419`). Errors: `SessionPersistenceNotFoundError` (nothing on disk, `:381`) and `SessionAlreadyOwnedError` (an active write handle already owns the id, `:377` → `storage.ts:429-432`; `open`'s catch frees the claim and joins a lock-release failure into an `AggregateError` `:400-418`). The handle starts at the stored event count (`:393`), so `handle.append(newEvents)` must start at that seq (`assertContiguous`, `storage.ts:323`); `handle.flush()` is the durability barrier.

**The running-Session path is the same one.** `AgentLoop.resumeWith` does `handle = await persistence.open(id, 'write', { signal })`, `handle.read(0, undefined, …)`, then `handle.append(closers)` (`core/agent-loop/src/index.ts:842-864`); a fresh Session uses `persistence.create(...)` (`createStoredSession` `:679-687`) plus `appendUnstoredSuffix` `:698-706`. The backend routes *live* events into whichever write handle holds the id: `ctx.on('session/event', (session, event) => { this.writers.get(session.id)?.enqueueLive(event, …) })` (`session-persistence-jsonl/src/storage.ts:534-539`; `adopt()` binds a write handle as the writer `:482-486`). A plugin holding `open(id,'write')` therefore receives the live Session's events automatically — and must **not** hand-append what a live Session is already emitting for that id, or the shared cursor breaks contiguity.

**Replace a stored log: no.** Nothing overwrites or truncates an existing log. `create` refuses an existing id (`SessionAlreadyExistsError` jsonl `index.ts:323-325`) and materialization refuses to publish over an existing committed log — `rejectExistingLog`: `'refusing to materialize "<id>": a log already exists on disk (open it instead)'` (`:1260-1270`). The only in-tree "replacement" is the format-migration path publishing a new *current* generation for a **historical** (older-version) artifact (`publishStoredMigration` `:692-714`); in-place truncation exists only as crash-tail repair (`truncateTornTail` `:889-893`, `repair` `:1364-1369`) and append rollback (`rollbackAppend` `:1354-1362`).

**If a log is deleted while the client has it open** (no delete API exists, so this is out-of-band): open read handles fail — `resolveCurrentLog` → `undefined` with no pending entry → `SessionPersistenceNotFoundError` (`storage.ts:143-153`), and a shrunken log trips `'stored log shrank below a previously observed prefix'` (`:172-173`); `stat()` returns `undefined` (jsonl `index.ts:462-466`); `list()` silently skips the missing artifact (`:499-502`). **Hazard:** `appendLines` opens with `open(path,'a')` (`:1327`), which *creates* a missing file, so an append through an existing write handle after an out-of-band delete recreates a **header-less** log; the next read then fails as corrupt (`:952` `'empty or header-less Zstandard session log'`, `:791-801`). The client keeps showing the row until its next pull (`ctx.sessions.refresh()`) — nothing pushes a removal, since `api-session/removed` comes only from `session/disposed` (`api/session-controller/src/index.ts:170-172`).

## Practical caveats for the mirroring design

1. `create` validates the header (JSON-lossless, `createdAt`, seeded/cut, v4 field set) but **never** validates event vocabulary on write; a bad `type` silently produces an unreadable log. Mirror events must be real `SessionEvent`s with dense `seq` from 0 and known types (or `ignorable: true`).
2. `create` is process-local until the first `append`/`flush`; only a resolved `flush` promises restart survival.
3. Writing a log does not put the Session into any workspace's durable `sessionIds`; it renders under *Ungrouped* once the client list has it. `archiveSession` requires the id to be live or in persistence (`workspace/src/index.ts:366-368`, `sessionKnown` `:470-475`).
4. The client learns of a newly written log only via `ctx.sessions.refresh()` (client) or a Host `api-session/added` emit — there is no watcher and no poll.
5. If the mirrored id is also live in the same Host, `open(id,'write')` throws `SessionAlreadyOwnedError`, and the live-routing listener would feed a plugin-held write handle; never double-append.
